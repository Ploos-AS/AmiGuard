# M2.2h — Safe-test clean-corpus preflight

## Goal

Add a read-only host-side preflight gate between safe-test proposal generation and native activation.

The gate proves two things using local files:

1. the proposed signature still matches the exact qualified positive artifact;
2. the proposed signature does not match any supplied known-clean file.

This milestone does not activate the proposal, does not modify signature metadata, and does not require FS-UAE because native scanner behavior is unchanged.

## Tool

`tools/preflight_safe_test.py` accepts:

- a `status=safe-test` proposal generated by `tools/promote_safe_test.py`;
- the exact local positive artifact used for acquisition/promotion;
- one or more local known-clean files.

Example:

```sh
python3 tools/preflight_safe_test.py \
  /tmp/eicar-standard-av-test-safe-test.json \
  ~/Downloads/eicar.com.txt \
  /path/to/clean/file1 /path/to/clean/file2 \
  -o /tmp/amiguard-eicar-preflight.json
```

The tool verifies the positive SHA-256 against `sample_sha256`, validates the safe-test semantics, rejects the positive artifact if it is accidentally included in the clean corpus, and reports each clean file's SHA-256 and match result.

A preflight passes only when:

- the positive hash matches the proposal;
- the positive artifact matches the proposed signature;
- at least one clean file is supplied;
- no clean file matches the proposed signature.

The report always records `malware_claim=false` and `native_activation=false`.

## EICAR note

The initial EICAR proposal uses an exact full-file 68-byte signature at offset 0 with an all-`0xff` mask. This deliberately favors specificity over generalized EICAR-family detection. False-positive risk is consequently expected to be very low, but the clean-corpus gate is still mandatory before native activation.

## Acceptance

Run:

```sh
make check
```

Acceptance requires all existing host tests plus `tests/test_preflight_safe_test.py` to pass.

## Next gate

After a real local EICAR preflight report passes, the proposal may be reviewed for controlled repository activation. Activation means replacing the research record with the reviewed `safe-test` metadata, regenerating `src/file_signatures_generated.inc`, running full host/CI qualification, and then performing visible A500/68000/Kickstart 1.2/512 KiB runtime qualification proving the output is `TEST-SIGNATURE` and never `INFECTED`.
